01Project Scope

From single-axis to a full coordinated platform.

This project extends the earlier single-axis simple-motion work into a full multi-axis coordinated platform: a Delta-style parallel robot with three joint axes, a rotary tool axis, and three virtual Cartesian axes tied to a CIP coordinate system. A 10-step procedural sequence drives MCLM coordinated linear moves through the Cartesian workspace, then calls a cam-profile calculator and launches two MATC time-driven cam moves to trace a parametric 8π-radian spiral in X/Y while Z steps. Each axis also owns its own Equipment Module with a PackML-aware CM00 procedure for jog/stop/error handling.

02System Architecture

One unit, seven EMs, two coordinate systems.

The DeltaBot controller is a 1756-L81E ControlLogix running Studio 5000 Logix Designer. The project is structured under ISA-88 / PackML conventions: a single unit (UN01_ExampleMachine) holds the procedural logic, while each physical axis is wrapped in its own Equipment Module. All motion runs over EtherNet/IP CIP Motion with Time Sync — every servo drive clocked from the same grand-master on the backplane, so coordinated linear moves execute on a common time base.

Layer 01

Unit Procedure

UN01_ExampleMachine with UP00_Procedure (master 10-step ladder), UP01_PackML, UP02_Transform, UP03_SpiralCalcPts, and UP10_SpiralCamCalcPoints.

Layer 02

Equipment Modules

Seven EMs (EM01_Axis_J1 … EM07_Axis_Z), each holding a PackML-aware CM00_Procedure that maps unit step flags into per-axis motion instructions.

Layer 03

Coordinate Systems

Cart_Coor for tool-tip Cartesian commands; Delta_Coor for the joint frame. UP02_Transform handles delta forward/inverse kinematics between them.

03Hardware & Axes

Kinetix 5700 servos, virtual Cartesians.

The robot exposes seven motion axes and two coordinate systems. The three delta upper arms and the rotary tool run on Kinetix 5700 drives over the device-level ring; the X / Y / Z Cartesian axes are AXIS_VIRTUAL tags that live only inside Cart_Coor. The coupling between joint space and Cartesian space is provided by UP02_Transform, so MCLM moves are written in tool-tip coordinates and the transform resolves joint angles in real time.

04Unit Procedure UP00

Master choreography, live-computed accel.

UP00_Procedure is a 14-rung ladder that sequences ten steps using a set-reset state pattern. Step transitions key off either the .PC (process-complete) bit of the preceding MCLM, the .DN of a wait timer, or the .DNs of the two MCCP cam-profile calculations. The same motion-math block is repeated at every linear-move step — once per step, live at every scan — so accel/decel are recomputed from the current robot position rather than assumed.

// Per-axis distance from current position to next target distance[0] := ABS(Cart_Coor.ActualPosition[5] - moveN[0]); // X error distance[1] := ABS(Cart_Coor.ActualPosition[6] - moveN[1]); // Y error distance[2] := ABS(Cart_Coor.ActualPosition[7] - moveN[2]); // Z error // Size the ramp so we reach MoveSpeed over half of the mean per-axis distance accel := (MoveSpeed ** 2) / (0.5 * (distance[0] + distance[1] + distance[2]) / 3);

A first-principles way of sizing the ramp: a short step uses a gentle ramp and a long step uses a stiff one. All moves then execute with the following MCLM parameters:

05Spiral Cam Profile

Build the geometry once, play it back in time.

Steps 7–8 draw a parametric 2-revolution spiral in the X/Y plane. Rather than stream a coordinated path, the program builds two cam profiles (one for X, one for Y) as a function of a common time-base master, then runs MATC on each virtual axis to play the cam back in time-driven mode. A classic trick when the workspace path is periodic or analytic: the PLC computes the geometry once, and the motion planner interpolates the rest.

UP10 — build the cam points (Structured Text)

A 14-line ST routine fills the Spiral_X_Cam and Spiral_Y_Cam CAM arrays with 101 points over 8π radians. Radius R = 2.0 grows linearly with θ, giving the classic Archimedean spiral r = Rθ.

NumOfPoints := 101; R := 2.0; FOR Index := 0 TO NumOfPoints-1 DO Theta := Index * (8 * pi) / NumOfPoints; Spiral_X_Cam[Index].Master := Index; Spiral_X_Cam[Index].Slave := R * Theta * COS(Theta); Spiral_X_Cam[Index].SegmentType := 0; // linear Spiral_Y_Cam[Index].Master := Index; Spiral_Y_Cam[Index].Slave := R * Theta * SIN(Theta); Spiral_Y_Cam[Index].SegmentType := 0; END_FOR;
Fig. 06 / UP10 — Spiral Point Generator
Structured-text routine populating the two CAM arrays. 101 points over 8π radians is two full Archimedean turns.
Fig. 07 / UP03 — MCCP Cam Calc
Two parallel MCCP blocks convert the point arrays into executable cam profiles (Spiral_XCam_Pro, Spiral_YCam_Pro). The rung latches UP_Exec_StepDn_07 once both .DN bits are high.

Once the profiles exist, each Cartesian virtual axis calls MATC (Motion Axis Time Cam) to play its half of the spiral. Because MATC is time-driven, the spiral traces itself autonomously on each axis — X and Y share nothing but the common time base, yet produce a smooth 2D path because both cams were built from the same Theta sweep. Meanwhile Axis_04_R runs a short jog sequence in its own EM so the tool spins while the spiral draws.

06Equipment Modules

The same CM00 pattern, per axis.

Each axis EM owns an identical 8–9-rung CM00 pattern that maps unit step flags into motion instructions on that axis: a NOP header; a first-scan COP of MI_Init into the working motion-instruction tag; a step-bit clear on first scan, UP_Resetting, or UP_Idle; a No_Steps_Active helper; a Step_1 seed on UP_Execute; the axis's actual motion instructions; and an AFI-guarded error latch into EM_ProcedureError[EM_Number]. The differences live in the middle — the R-axis jogs, the X / Y axes run MATC, the J-axes get transform output.

Fig. 10 / EM03_Axis_R — MAJ Jog
Rung 5 — an MAJ starts the tool spinning at 0.1 units/sec with parameterized accel/decel of 100 units/sec², S-Curve profile, Jerk = 100 % of Time, during UP_Exec_Step_08 (while the spiral is playing).
Fig. 11 / EM03_Axis_R — MAS Stop
Rung 6 — an MAS kills the jog at UP_Exec_Step_09, changing decel but preserving the decel-jerk so the tool stops smoothly before the final return move.
07Tuning & Trend Analysis

Jerk is the production knob.

Three trend experiments visualized how accel/decel jerk shapes the Cartesian path during the 6-step linear sequence (before the spiral). Cart_Coor.ActualPosition[0..2] (X, Y, Z) plotted against time on the same chart; a companion chart plots X vs. Z to show the projected path. Cycle time trades almost linearly against mechanical friendliness on the delta parallelograms.

Jerk = 100 % of time — trapezoidal, fastest cycle

Fig. 12 / X/Y/Z vs Time @ 100 % Jerk
Total cycle ≈ 45 s. The ramps are sharp-elbowed — jerk is effectively infinite at the transition, mechanically harshest but temporally fastest.
Fig. 13 / X vs Z Projection @ 100 % Jerk
Motion dominated by straight legs (pure trapezoidal), giving a crisp polygonal path through the workspace.

Jerk = 50 % of time — half-S, half-trap

Fig. 14 / X/Y/Z vs Time @ 50 % Jerk
The shoulders of each ramp round slightly; cycle lengthens a few seconds but peak jerk is halved.
Fig. 15 / X vs Z Projection @ 50 % Jerk
Corners stay tight because termination type is still actual tolerance — the motion planner completes each step before the next launches.

Jerk = 10 % of time — full S-curve

Fig. 16 / X/Y/Z vs Time @ 10 % Jerk
Ramps deeply rounded (essentially an S-curve). Cycle time grows noticeably, but mechanical stress on the delta parallelograms drops dramatically.
Fig. 17 / X vs Z Projection @ 10 % Jerk
Projected path still linear segment-by-segment because each step terminates individually, but intra-segment motion is gentler.

Tuning takeaway. Jerk percentage trades cycle time for mechanical friendliness on an almost linear basis for this workload — 10 % jerk is ≈ 1.5× the total time of 100 % jerk but is what you would run in production on a delta, because parallel kinematics amplifies shock at the tool through all three J-axes simultaneously.

08Engineering Takeaways

What the build actually taught.

Coordinate Systems
  • Programming in Cart_Coor over per-axis moves
  • UP02_Transform doing inverse kinematics under the hood
  • Pure Cartesian geometry in UP00 — review-friendly
  • Joint frame isolated to one routine
Cam Profiles
  • Build geometry once (UP10), execute many (MATC)
  • MCCP arrays → CAM_PROFILE objects
  • Time Scaling = 0.15 for 7× playback
  • Cheaper per scan than streamed paths
Live-Computed Accel
  • accel = MoveSpeed² / (½ mean-distance)
  • Position-robust across homing offsets
  • Short steps get gentle ramps automatically
  • Long steps stiffen the ramp to hit speed
PackML in Every Module
  • UP_Idle / UP_Execute / UP_Resetting in every CM00
  • Each axis independently agrees with the unit
  • R-axis jog + X/Y cams run in parallel cleanly
  • No cross-contamination between modules
CIP Motion Practice
  • EtherNet/IP with Time Sync grand-master
  • Kinetix 5700 H008 / H015 drive sizing
  • Device-level ring topology
  • Common time base for coordinated moves
Jerk Tuning
  • Jerk is the first-order lever on mechanical stress
  • More useful to vary than speed itself
  • 100 / 50 / 10 % experiments documented
  • Production knob, not a debug parameter
09Outcome

Ten steps, two cams, seven coordinated servos.

The final deliverable is a working DeltaBot motion application: ten coordinated linear moves through Cartesian workspace, a parametric 8π-radian Archimedean spiral played autonomously on two virtual axes via time-driven cams, a rotary tool that jogs in parallel for the duration of the spiral, and a clean PackML hand-off back to Idle at the end of the cycle. Beyond the working demo, the build was a concrete walkthrough of how a modern multi-axis motion project comes together — CIP Motion time sync, coordinate systems with inverse kinematics, cam-profile geometry computed once and replayed in time, and a PackML-shaped supervisory layer that lets independent axes execute coordinated choreography without cross-contamination.
